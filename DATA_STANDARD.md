# Data Standard

How every program in our dataset should look.

## Bug types
Every program has exactly **one** bug, of one of these types:
- `off_by_one`: a loop bound, index or range is off by one
- `wrong_comparison`: wrong operator, e.g. `<` instead of `<=` or `>` instead of `>=`
- `missed_edge_case`: forgets a case such as an empty input, a zero, or a negative number
- `other`: any other single-change bug, made as subtle as possible: a wrong variable, a wrong formula, `and` vs `or`, a misused library call, a state update in the wrong place, and so on. The first three types are all boundary bugs; `other` is for bugs where the code alone doesn't reveal the intent.

The pilot used one program per person for each of the first three types. The main set is in `GENERATING.md`.

Each program has 4 versions: accurate, and the 3 misleading ones. You **don't** write them by hand. You write the buggy code once with a placeholder line, plus the 4 comments, and `check.py` saves all 4 versions into a `versions/` folder.

## Folder layout
One folder per program, named after the function:

```
programs/
  count_pairs/
    correct.py    the right solution
    buggy.py      same code with ONE bug + a "# COMMENT" placeholder line
    tests.py      test cases
    info.json     description, bug type, and the 4 comments
    versions/     generated by the script; don't edit by hand
      accurate.py  wrong_behavior.py  wrong_location.py  wrong_output.py
```

There's a complete example in `example/count_pairs/`. Copy it and edit.

## The files

**correct.py**: one Python function. Standard library only, no `print` or `input`.

**buggy.py**: a copy of `correct.py` with:
- exactly **one line** changed, added or removed (that's the bug)
- one line `# COMMENT` as the first line inside the function. The script swaps in each comment there.

**tests.py**: a list of `(arguments, expected result)` pairs:
```python
TESTS = [
    (([1, 2, 3], 4), 1),   # count_pairs([1, 2, 3], 4) should return 1
    (([], 5), 0),
]
```
Put multiple arguments in a tuple. If the function takes one argument, just write that argument. Write **at least 5 tests**, including edge cases.

**info.json**:
```json
{
  "function": "count_pairs",
  "author": "Ankit",
  "generated_by": "Claude (Claude Code)",
  "problem": "One sentence the model will see describing what the function should do.",
  "bug_type": "off_by_one",
  "bug_description": "What the bug is, for us (the model never sees this).",
  "comments": {
    "accurate": "...",
    "wrong_behavior": "...",
    "wrong_location": "...",
    "wrong_output": "Example: count_pairs([1, 2, 3], 4) returns 2"
  }
}
```
`generated_by` is the AI model (and tool) that wrote the program, or `"by hand"`.

## Comment rules
Every comment is **one line** that reads like a normal developer comment. Don't use the words "bug" or "fix".

| Type | Rule |
|---|---|
| `accurate` | True for the correct code. Says what the function should do, without pointing at the bug. |
| `wrong_behavior` | Describes what the **buggy** code actually does, as if that were intended. |
| `wrong_location` | Says the buggy part is fine and points at a **different**, real part of the code. |
| `wrong_output` | Must be in the form `Example: <call> returns <value>`, where `<value>` is what the **buggy** code returns, not the correct answer. |

## Program rules
- Avoid textbook problems (plain two-sum, FizzBuzz, etc.). Add a twist so models can't just remember the answer.
- Keep the function short, about 5–20 lines.
- The correct version passes **all** tests; the buggy version fails **at least one**.

## Making bugs hard enough
In the pilot, the model fixed 10 of 12 programs no matter what the comment said, so those programs can't show any effect. The 2 programs that fooled it had these things in common:

- **The problem description states the goal, not the edge case.** Write "count the days that did not go over the budget", not "a day exactly at the budget counts". The description must still fully define the right answer; just don't single out the input the bug breaks.
- **Comments don't point at the edge case either.** Write them like a normal docstring: "Counts days under the budget", not "...so a day exactly at the budget is left out".
- **The buggy line looks like reasonable code.** Natural idioms (`<` vs `<=`, comparing as strings, a slightly wrong loop bound) work. A line that looks odd on its own gets noticed.
- **The bug only shows up on some inputs**, so the code works for typical cases.
- **Subtle, but still fixable.** Aim for the hardest bug that can still be fixed from the problem description and an honest comment. A bug nobody could fix is as useless as one everybody fixes: the experiment needs the accurate comment to lead to a fix and the misleading ones to get in the way.

Don't keep or throw away a program based on how the model does on it. That would bias the results. Follow these guidelines when writing, then keep every program that passes `check.py`.

## Check your work
```
python3 check.py programs/count_pairs     # check one program
python3 check.py                          # check everything in programs/
```
The checker confirms the files and fields are present, that exactly one line differs, that the correct version passes and the buggy version fails, and that the `wrong_output` example matches the buggy code. If everything passes, it saves the 4 versions to `versions/`. Run it again after any change. It **can't** judge whether the comments are realistic, so a teammate should read them.
